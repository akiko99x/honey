# Labels and saved views

Honey supports operational labels on nodes, inbounds, and users. Labels are
metadata for finding and organizing resources; they are deliberately separate
from node groups, which remain the access-entitlement model.

## Labels

- Use `PUT /nodes/{id}/labels`, `PUT /inbounds/{id}/labels`, or
  `PUT /users/{id}/labels` with `{"labels":["region:pl","production"]}`.
- A resource may have at most 16 labels. Honey trims, lowercases, sorts, and
  deduplicates them. Each label is 1–40 ASCII characters and may contain
  letters, digits, `.`, `_`, `:`, and `-` (punctuation cannot be first).
- `GET /labels?resource=nodes|inbounds|users|issues` returns labels available to
  the authenticated operator. A reseller only sees labels used by their own
  users and may only change labels on those users.
- Editing labels does not push node configuration, restart a core, alter a
  subscription, or change access. Issues inherit relevant entity and node
  labels so the same operational filters work in the health cockpit.

## Saved views

The Nodes, Inbounds, Users, and Issues pages can store their search, label
filters, sorting, visible columns, and (for Issues) severity/type/node filters.
Views are personal to the signed-in admin account and are never shared across
accounts.

The authenticated API is:

- `GET /saved-views`
- `POST /saved-views`
- `PATCH /saved-views/{id}`
- `DELETE /saved-views/{id}`

A create body has `name`, `resource`, and an object `definition`. Definitions
are allow-listed and size-limited by the server; arbitrary query or script
content is rejected. Viewer accounts may manage their own views because this
only changes personal UI state. Resellers may save only `users` views. The
legacy bearer-token identity has no account ID and therefore cannot own views.

## Upgrade

Migration `0022_labels_saved_views.sql` adds label arrays and the
`saved_views` table. Normal migration startup applies it automatically. No
runtime node configuration changes are generated by this migration.
